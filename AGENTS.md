# herdr-fleet

A herdr plugin that starts and manages a team of named coding agents from a per-repository fleet file. Read `docs/design.md` first: it is the spec, and behaviour changes start there. `docs/requirements.md` holds the problem and the facts about herdr 0.9.4; `docs/survey.md` the prior art.

- Check herdr syntax against the installed binary (`herdr <group> --help`, `herdr --skill`) and https://herdr.dev/docs/plugins/.
- Never send keys or prompts to a herdr pane in state `blocked`, never answer another agent's permission prompt, and never run bare `herdr`. The plugin itself presses keys only through `Herdr.agent_send_keys`, and only those of design 23.7 and 23.11 (one Enter on the exit confirmation its own quit provoked, `interrupt`'s keys, and one Ctrl-U after them when the interrupted prompt came back into the input); add no other key path.
- Don't push to a remote without the owner's explicit approval.

## Architecture

`bin/herdr-fleet` puts the plugin root on `sys.path` and calls `herdr_fleet.cli.main`, which parses arguments, runs the common preconditions (`context.preflight`) and dispatches to an operation in `ops.py` (up, restart, swap, kickoff, down, go, peek, interrupt, ui, install-cli), `checks.py` (status, drift, doctor) or `menu.py` (the `manage` and `go` popups). Operations work on a `context.Ctx` holding the herdr client, the parsed fleet file (`fleetfile.py`), the state file (`state.py`) and the plugin config, and return a `Report` that the CLI prints and maps to exit codes 0/1/2/3. `bringup.py` finds or creates the workspace, classifies each seat (live, adopted, recorded pane, or needs a pane) and starts it; `placement.py` splits the panes seats need, in chain or grid mode (design section 14), using the pure plan in `layout.py`; `tile.py` re-tiles live seats with `pane move` only (design 15.1), anchoring on the `[layout] top` seat when one is set so its pane spans the width above the grid (design 26; `placement.place_band` builds that band on a fresh workspace and `placement.band_check` tells `up` when `tile` is needed); `seats.py` holds every interaction with a live agent: the shell-prompt check, `start_in_pane` (with the `agent_pane_busy` retry), `safe_prompt` (the only path for text to an agent; it refuses anything not `idle` or `done`, then runs the presence guard) and `quit_agent` (through `safe_prompt`, so the guard runs before every quit command too; when the agent is still there 3 s later it reads `agent read NAME --lines 16` once and presses one Enter only on the kind's exit confirmation in `seats.EXIT_DIALOGS` with the exit line highlighted, never from the popup, design 23.7). `interrupt_agent` presses a working seat's `seats.INTERRUPT_KEYS` (or the `[interrupt]` table of the fleet file, then the plugin config), 300 ms apart, and waits for idle or done; `ops.op_interrupt` is its only caller, after the state check, the presence guard and an `agent read` that shows no dialog, and it alone presses `ctrl+u`, once, when the prompt line read after the interrupt holds text (design 23.11); `ops.op_peek` prints `agent read` and writes nothing. `presence.py` is that guard (design 21.2 as 23.11 amends it, invariant 19): `typing` reads the pure `prompt_line` over `pane read PANE --lines 12` (glyphs in `seats.PROMPT_GLYPHS` and `seats.PROMPT_PLACEHOLDERS`) for every target pane, focused or not, and holds the text (status `typing`) while the line holds text or no prompt line is on screen; only then does `owner_pane` (`pane get` focused, then `workspace list`) choose the detail, `owner typing in <pane>` or `text in its input (<pane>); press Ctrl-U there to clear it`; the lines are read for that alone and kept nowhere. `herdr.py` is the only module that executes herdr, and it refuses `pane send-keys`, `pane send-text`, `pane run`, bare `herdr` and `agent send-keys` before spawning anything; `agent send-keys` runs only from `Herdr.agent_send_keys`, which accepts `enter`, `esc`, `ctrl+c` and `ctrl+u` alone (invariant 21); `ctrl+u` is restricted to the one post-interrupt cleanup path of 23.11. Live herdr facts the code relies on are in `docs/design.md` section 12; in particular, pane records carry no agent `name`, so read names through `agent get` (`Herdr.pane_agent`), never from `pane get`/`pane list`. `kickoff.py` renders templates; `notify.py` wraps `herdr notification show`. `messages.py` implements `send` (the inbox note first, design 23.1; the sender is `caller_record`: the pane's herdr name, else the one contact matching that agent, else a usage error, and `owner` only without an agent, 23.3; only `send --now` and `deliver NAME --now` may prompt a `working` agent, still through `seats.safe_prompt` with `seats.SEND_ALLOWED`; a plain `send`, the flush before it, `deliver` and `watch` leave a working seat's messages queued whatever their `queued_by`, design 21.1), the append-only message log `.herdr/messages.jsonl` and owed replies; `contacts.py` resolves `[[contacts]]` against `agent list` (contacts are messaged, never managed); `statenote.py` edits `## KEY` sections of the state note; `permissions.py` is the advisory Claude Code permission check in `doctor` (design section 16). `gitinfo.py` holds the read-only git helpers (every call sets `GIT_OPTIONAL_LOCKS=0`; nothing fetches, prunes or writes); `worktrees.py` implements `worktrees` and `checks.py` the `fleet file vs git` doctor check on top of it; `context_size.py` shares Claude/Codex provider resolution, session-specific lookup and bounded backward reading between `status --context` and the board (design sections 17 and 29); Claude counts input plus cache creation/read, Codex uses last-request total and optional reported window, never lifetime counts or inferred limits. Only usage/window numbers, timestamp and source leave the reader, and neither provider's source root is written; `ack` and `--fyi` live in `messages.py`. `inbox.py` holds the mailboxes under `.herdr/inbox/<name>/{new,cur}` (ids, message files, batch rendering, moves, ttl; pure file work, no herdr and no log), `messages.py` adds the delivery engine every path shares (`prompt_mailbox`: expire, batch, `safe_prompt`, move to `cur/`, log `delivered`), and `mailroom.py` implements the `deliver` and `inbox` commands (design section 18; `inbox --wait` polls the mailbox's files every second on `ctx.clock` and reads under the same mailbox lock as the watcher, 23.2). `timers.py` owns daily timer validation, planning, metadata-only occurrence history, crash recovery and read-only inspection (design section 30); `timer_calendar.py` provides one calendar interface for `zoneinfo` and the isolated native-TZ fallback, with a bounded date batch per active schedule. Timer locks precede mailbox locks, chosen ids persist before enqueue, and the scheduler never prompts or manages agents. Only the existing watcher delivery engine submits timer mail. `messages.unsettled` joins recovered timer sends by id even when delivery was logged first, while generic ordering stays unchanged. `watch.py` is the foreground watcher of design 18.6 (`.herdr/watch.lock`, one `agent wait --until idle --until done` thread per mailbox, delivery through `messages.prompt_mailbox`, and the hold of design 21.2 while the owner types in a seat's pane). On a terminal, without `--log`, it draws the board of design 24 in the strip: the waiter threads post an event to `Watcher.events` with every line they say and every wait that returns, and between passes `watch.BoardView` drains that queue, rebuilds the model after an event or every 5 s, draws, and reads keys; every line then goes to `.herdr/watch.log` and the footer instead of stdout (a `LineSink` catches what other code prints), and the delivery paths are the same as in log mode. `board.py` holds the model (`build`: one `agent list`, `pane get` for a working seat's title, `agent read --lines 16` only for a blocked seat and only up to four lines of its dialog through `seats.dialog_lines`, `state_seen`, the mailboxes, `messages.owed` parsed again only when the log changed, the transcripts' context size and optional window through the shared reader, cached by provider/root/session and path/mtime/size), the pure `render(board, width, height, colours)`, lines of `(text, style)` spans, and the view stack of design 25 (`BoardPage`, the root; `SeatPage`, `FleetPage`, `OwnerPage`, `ContactPage` and `Body`, each with `load`, `render` and `key`, a key giving back an action tuple that `BoardView.act` carries out); `tui.py` is the `Screen` it draws on (`size`, `draw`, `getch`, which also returns clicks as `("click", row, col)`; `CursesScreen` imports `curses` lazily, so nothing else needs it, and `FakeScreen` records draws and replays scripted keys and clicks for the tests) and `tui.zoom`. The board's keys only call existing functions: `g` `ops.op_go`, `p` `ops.op_peek`, `a` `messages.op_ack` with `--reason "from the board"` as `owner`, `d` `Watcher.deliver` for idle or done seats, `z` `Herdr.pane_zoom_toggle` on the strip's own pane (an explicit pane id from `HERDR_PANE_ID`, else the state's watch pane; never `--current`, design 25.7); drawing and navigation prompt nothing and send no agent key; `d` uses the watcher's guarded delivery path, and `agent focus` and explicit own-pane `pane zoom` run only on a key (invariant 22). `hooks.py` writes the opt-in Claude Code hooks of 18.7 into `.claude/settings.local.json`, whose `inbox --hook` side lives in `mailroom.py` and prints nothing on any error. `watchpane.py` is the strip `up` opens to run the watcher below the seats (design section 19): a plugin pane recorded as `"watch"` in the state file, never a seat. `labels.py` names every live seat's pane after its seat or its `label` key (`pane rename`, design 22.1) at the end of up, restart, swap, kickoff, tile and status, and `down` clears the name of a seat pane it leaves at a shell; no other pane is ever renamed. `go` (`ops.op_go`, design 22.2) resolves a name as `send` does and runs `agent focus`, the one command that moves the owner's focus, from the CLI, the `manage` popup, the `go` popup (`menu --go`) and the board's `g` key. `seen.py` records each seat's `state_seen` (design 20.5) for every command that reads seat states, through `state.record_seen`, which rewrites only that field under a lock on `.herdr/` that `save_state` also takes. `crossfleet.py` finds the other fleet of a live agent that is neither seat nor contact (its `cwd`, then `foreground_cwd`) and appends `send` and `delivered` entries and the message file there (design 20.8); it never creates a `.herdr/` directory in another repository. `scaffold.py` implements `init` (design section 13): pure file writing, no preflight and no herdr command except the optional notification. No third-party dependencies; `tomli` is vendored under `herdr_fleet/_vendor/` for Python < 3.11. Code must run on Python 3.8+: `from __future__ import annotations`, `typing.List`/`Optional`, no `match`, no `X | Y`.

## Build and test

There is no build step. Run the suite with an available Python below 3.11 and one at or above 3.11 before handing work back; substitute their absolute paths when needed:

```bash
python3.9 -m unittest discover -s tests -v    # vendored tomli
python3.12 -m unittest discover -s tests -v   # standard-library tomllib
python3 -m compileall -q herdr_fleet bin/herdr-fleet
```

Tests use the fake herdr in `tests/fake_herdr.py`; never point them at a live herdr. `tests/support.py` checks every test's call log against the safety invariants of design section 7, so a new scenario is automatically a safety test (since 0.11.0 it also fails a `pane rename` of a pane that hosts no seat or to a name other than that seat's, and an `agent focus` not run by `go` or `menu`; since 0.12.0 any `agent send-keys` but one `enter` from restart, swap or down right after an `agent read` that showed the highlighted exit confirmation, the kind's interrupt keys from `interrupt` to a seat working at its last `agent get` whose screen it read, or one `ctrl+u` from `interrupt` after an `agent read` that showed text in the input, and any from watch, menu, deliver or a dry run, and any `agent prompt` to a pane whose prompt line held text, focused or not; script it with `fake_herdr.exit_dialog_on_quit`, `show_exit_dialog`, `interrupt_results` and `restore_prompt_on_interrupt`; since 0.13.0 an `agent focus` from `watch` that does not follow a `g` or a number key replayed by the fake screen, a `pane zoom` that does not follow a `z` or is not on the strip's own pane, one per key, and an `agent read` from `watch` of anything but a seat whose state at the command's last `agent list` was `blocked`, unless right after a `p`; drive the board with `tui.FakeScreen(keys, on_key=self.log_key)`, `watch.is_terminal` and `tui.open_screen` patched, as `tests/test_section24.py` and `tests/test_section25.py` do); only prompts issued by `send --now` and `deliver --now` may reach a `working` agent (`support.typed_ahead_allowed`), and no prompt may reach a pane the fake recorded as the owner's with text on its prompt line or no prompt line on screen (`owner_typing`; script it with `fake_herdr.focus`, `type_in` and `show_dialog`). For manual validation, follow the current scratch-fleet workflow in `docs/testing.md`; historical release evidence lives in `docs/design.md`. Live smoke tests are run by the designer or owner, never by the test suite. For starter examples or contact-capacity changes, follow design section 27 and `tests/test_section27.py`: seats and contacts share board capacity and every hidden row counts in `+N more`.

## Public examples and publication

For example, fixture or documentation changes, use the synthetic `examples/team` identifiers and paths. Review the whole tracked tree for deployment details and copied operational text (design section 28). The root `.herdr/` is local development configuration; leave its files on disk and keep it outside the public tree. Preserve public package identity, upstream credits and licence attribution. Current-tree checks do not sanitize old Git history or authorize publication.

For daily timers, follow design section 30 and `tests/test_section30.py`. History-bearing watchers reconcile removal even with an empty timer list and reload timer edits in board and log modes; pristine no-timer fleets create no timer files or calendar child. Timer inspection is read-only, and dry-run is entirely offline. Public timer examples must use synthetic requests; production acceptance is separate owner/coordinator work.
